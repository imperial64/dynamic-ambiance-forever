## 1. REJECTED — "no `RegisterEvent` anywhere in the file"

agy's highest-severity finding, and it is false. `AmbianceCost.lua:1010-1011` registers
`PLAYER_LOGIN` and `PLAYER_LOGOUT`; `:1013-1018` handles them and calls `restorePhase()` on
logout. `README.md:255` is accurate.

The search missed it because registration goes through
`pcall(frame.RegisterEvent, frame, event)` rather than `frame:RegisterEvent(...)` — the
indirection defeats a pattern match for `:RegisterEvent`. That indirection exists on purpose:
an unknown event name raises and aborts the rest of the file on this client.

**Kept from it:** the second half of the finding is sound. If a bench raises inside
`autoBench`, the `step()` chain aborts and the synchronous CVar restore at the end of
`runBench` never runs. The `PLAYER_LOGOUT` path does not cover that, because the addon is not
unloading. Worth a `pcall` around `fn()` in `measure()`.

## 2. ACCEPTED — the garbage budget models half the addon

`README.md:3` states the addon drives **both** Brightness and Contrast. Every cost figure in
the README models **one** CVar. Writes double; the poll does not, because `evaluate` already
returns both values from a single pass.

## 3. ACCEPTED — `autoBench` leaves the collector running

`AmbianceCost.lua:256`. `measure()` calls `debugprofilestart()`, runs the loop, and stops the
timer, with no `collectgarbage("stop")` — unlike `allocPerCall`, which does stop it. Thousands
of iterations of a 1864 B allocation inside the timed window guarantee step-GC fires inside
it, so **the per-call CPU figures for allocating calls include collector work**.

Affects `GetPlayerMapPosition`, `readPos` and `SetCVar`. Does not affect `evaluate` or the
ease step, which allocate nothing.

Direction: the reported costs are **over**-stated, so the "effectively free" conclusion is not
at risk. But the individual numbers are not clean and should be re-measured with the collector
stopped before being quoted precisely.

## 4. PARTLY ACCEPTED — vsync clamping explains runs 1-3, drift explains run 5

agy is right that runs 1-3 sat at a ~119.9 fps cap with CPU headroom, so injecting ~10 us of
work cannot move a wall-clock frame gap. That is a better explanation of those runs' null
result than the 1 ms quantisation the README gives, and it should be recorded.

agy is wrong that it explains the phenomenon, because it did not account for run 5, which was
**uncapped** (`useMaxFPS=0`, `vsync=0`) and ran at 238.8 / 214.0 / 190.2 fps across the three
phases. Nothing was clamped there. The README's drift argument is about run 5 specifically,
and it stands: `tuned` polls 22x less than `naive` for the same writes and cannot cost more,
yet measured slower.

Both explanations are true of different runs. The README should carry both.

## 5. ACCEPTED — `readPos` and the raw API bench are not comparable

`AmbianceCost.lua:154`. `readPos` wraps two `pcall`s, a `type()` check and an unpack around
the API call; the `GetPlayerMapPosition` row is bare. Reporting 4.38-5.71 and 4.91-7.91 side
by side invites reading the difference as noise when it is the safety wrapper, worth roughly
+0.5 to +2 us. They should be labelled as raw and wrapped rather than left to be compared.

## 6. ACCEPTED, and worse than agy stated

agy reproduced 139.3 us/s and called it exact. It reproduced **my arithmetic while inheriting
my inputs**, one of which is wrong (finding 11). Corrected below.

## 7. REJECTED as Blocking, accepted as a Note

A sandboxed LuaJIT with `jit`, `ffi`, `table.new` and `string.buffer` all niled would read as
the plain interpreter. True, and unfalsifiable by the current probe. But it requires a
deliberately disguised VM, and three independent signals agree on this client. Behavioural
falsification (deep tail recursion) would close it; it is not worth blocking on.

agy's two passes contradicted each other here — pass 1 listed the claim as correct and
well-evidenced, pass 2 marked it Blocking. Adjudicated rather than averaged: the evidence is
good, the theoretical hole is real, the severity is Note.

## 8. ACCEPTED — workloads discard Contrast

`AmbianceCost.lua:449`, `:464`. `(evaluate(px, py))` truncates to one return value, so the
frame-phase workloads model a single-CVar ease. Consistent with finding 2: the synthetic
workload under-models the real addon.

## 9. ACCEPTED — baseline closure captures no upvalues

`AmbianceCost.lua:612`. `function() return nil end` compiles without the `OP_GETUPVAL` that
every measured closure carries, so the subtracted overhead is slightly too small and all net
costs are slightly overstated. Conservative direction. Not worth re-measuring on its own.

## 10. ACCEPTED as a documentation gap

`collectorStops` proves `collectgarbage("stop")` halted the step collector. It cannot prove
`collectgarbage("count")` was not spoofed — a hook returning `prev + 56` each call would pass.
The guard should say what it proves rather than implying it certifies the whole API.

agy's `TABLE_BYTES` analysis (actual ~64 B vs the 56 B estimate) is correct and, as agy itself
concluded, does not matter: the 50% floor swallows the variance.

## 11. FOUND DURING VERIFICATION — the 47 writes/s constant was fabricated

Not an agy finding; surfaced by following its instruction to check that the constants appear
in the raw data rather than being back-fitted. They do not.

Measured writes per 10 s phase, across all five runs: **352, 353, 342, 281, 365** — about
**35/s**, not 47. The 47 came from multiplying 17% by the *env snapshot* frame rate (274 fps)
instead of the naive phase's actual rate (214 fps).

A second thing falls out of the same table, which the README also gets wrong: the **absolute
write rate is near-constant at ~35/s across every frame rate tested**, from 119 fps to 238.
Only the *percentage of frames* fell (29% to 17%). The README's claim that "the design
throttles itself for free" at high frame rates is therefore misleading — it does not write
less often, it writes on a smaller fraction of more frames. Write rate is set by how fast the
target moves against `WRITE_EPSILON`, not by frame rate.

## Corrected figures

Measured inputs: poll bundle 7.76 us (`GetBestMapForUnit` 0.61 + `readPos` 5.11 + `evaluate`
2.04), ease 0.088 us, write 0.79 us, position read 1864 B, write 822 B, ~35 writes/s, 10 Hz
poll, 214 fps (run 5 naive phase). `evaluate` is shared between both CVars; ease and write are
not.

| | one CVar (as published) | **two CVars (actual design)** |
|---|---|---|
| CPU | ~124 us/s, 0.012% | **~171 us/s, 0.017%** |
| garbage, moving | 47.4 KB/s, 167 MB/h | **76.2 KB/s, 268 MB/h** |
| garbage, at rest | 18.6 KB/s, 65 MB/h | **18.6 KB/s, 65 MB/h** |

At rest is unchanged: nothing writes, and the poll is shared.

The CPU conclusion survives unharmed — 0.017% is still free, and finding 3 means even that is
an overestimate. The garbage figure is 34% higher than published and is the number that
changes.
